## Requirement understanding

One line: Vanta is a Conduit plug-in. Connect it to give Claude, ChatGPT, Cursor, or any MCP-compatible AI live access, with credentials encrypted and every action logged.

The ticket asks for a new MCP connector so Agent-platform clients can query a tenant's live Vanta compliance posture — controls, test results, compliance documents, vendor risk records, personnel (including offboarding/employment status), device compliance, and open issues — without a human having to open the Vanta UI. "Credentials encrypted" and "every action logged" describe properties the platform's MCP gateway already provides for every connector (Header-only credentials, gateway-level call logging); they are not new capabilities this repo has to build. No specific tool, bug, or missing capability is named in the ticket — this is a from-scratch "new integration" request.

## Product design

### Goals / Non-goals

**Goals**

- Give Agent-platform clients (Claude, ChatGPT, Cursor, or any MCP-compatible client reached through the platform's MCP gateway) read access to a connected Vanta tenant's:
  - security controls and their status,
  - control test results,
  - compliance documents (policies/evidence) and their upload status,
  - third-party vendor risk records,
  - personnel records, including employment/offboarding status,
  - monitored-device compliance signals (disk encryption, screen lock, antivirus, last check-in),
  - open compliance issues/findings.
- Each capability above is reachable as a single, paginated "list or get-by-id" tool, so an agent can both browse (e.g. "which tests are failing") and look up one record by id.
- Credentials (a Vanta OAuth client id + secret) are supplied per request via the gateway's Header mechanism; the connector itself never stores or displays them.

**Non-goals (v1)**

- No write operations (e.g. changing a control's owner, uploading a document, closing an issue). The ticket's ask is "live access", not "make changes"; writes carry materially higher blast radius and nobody has asked for one. A follow-up ticket can add specific write tools if a real need appears.
- No support for Vanta Gov tenants (`api.vanta-gov.com`) or the Auditor API — no MSPbots tenant has asked for either.
- No webhooks/alerting — out of scope, this is a pull-based connector like the platform's other MCP connectors.
- Does not change how connectors are published/surfaced to tenants (`Published Connectors`, Capabilities) — that plumbing already exists and is untouched by this ticket.

### Acceptance criteria

- **AC1**: Given valid Vanta credentials, when an agent calls the controls tool without an id, then it returns a paginated list of controls (id, name, description, source, domains, owner, creation/modification dates).
- **AC2**: Given valid credentials and a specific control id, when the controls tool is called with that id, then it returns that single control; given an id that does not exist in the tenant, then it returns a `not_found` error (not a 500, not an empty list).
- **AC3**: Given a `status` filter (e.g. `NEEDS_ATTENTION`), when the tests tool is called, then only tests in that status are returned.
- **AC4**: Given valid credentials, when the documents tool is called, then it returns compliance documents with their `uploadStatus` (e.g. `Needs document`, `OK`).
- **AC5**: Given valid credentials, when the vendors tool is called, then it returns vendor risk records including `status`, `inherentRiskLevel`/`residualRiskLevel`, and review dates.
- **AC6**: Given an `employment_status=FORMER` filter, when the people tool is called, then only personnel whose employment status is `FORMER` are returned (the offboarding-status use case named in the "current state" of a security review).
- **AC7**: Given a specific person id, when the people tool is called with that id, then it returns that single person record.
- **AC8**: Given a `compliance_status` filter, when the monitored-computers tool is called, then only devices matching that compliance signal (e.g. `HD_NOT_ENCRYPTED`) are returned.
- **AC9**: Given `severity`/`status`/date-range filters, when the issues tool is called, then only matching issues are returned, each with `severity`, `status`, `dueDate`, and remediation fields.
- **AC10**: Given a request with no `X-Vanta-Client-Id` / `X-Vanta-Client-Secret` headers, when any tool is called, then the connector returns 401 with a body listing the two required headers (not a 500, not a silent empty result).
- **AC11**: Given credentials Vanta rejects (bad client id/secret), when any tool is called, then the connector returns a structured `unauthorized` error, not a raw 500 or an unhandled exception.
- **AC12**: Given a `limit` above Vanta's own ceiling of 100, when any list tool is called, then the connector clamps the request to 100 rather than rejecting it or passing an invalid value upstream; given a `next_cursor` from a prior page, when it's passed back in, then the following page is returned, and the last page reports `has_more: false`.
- **AC13**: Given Vanta returns 429 (on the token endpoint or an API call), when a tool call is retried a bounded number of times respecting `Retry-After` and still fails, then the connector returns a structured `rate_limited` error rather than hanging or crashing.
- **AC14**: Given two concurrent calls using different tenants' credential headers, when both are in flight at the same time, then neither tenant's token or data is visible to the other request (request-level isolation, not just "usually doesn't happen").

### Open questions

- OQ1 (not blocking, assumption documented): should v1 include any write tool (e.g. setting a control owner)? Assumed **no** — the ticket only asks for "live access", not changes. If a write capability is wanted, file it as a new, separately-scoped ticket so it gets its own blast-radius review.
- OQ2 (not blocking, assumption documented): Vanta Gov tenants are assumed out of scope for v1 (no MSPbots tenant on Vanta Gov is known). If one appears, the fix is additive (a second base-URL choice), not a redesign.

Neither question blocks implementation; both are proceeding under the stated assumption and are called out here so BA/INT acceptance can override if wrong.

## Tech design

### Conclusion

Build a new, read-only Python/FastMCP service in `MSPbotsAIFramework/vanta-mcp` (currently an empty scaffold) exposing 7 tools — one per Vanta resource area named in the ticket (controls, tests, documents, vendors, people, monitored computers, issues) — each able to either list (with filters/pagination) or fetch a single record by id. Credentials are a Vanta OAuth2 client id/secret pair read from request Headers; the service exchanges them for a short-lived access token on every call (never cached across requests, per the platform's request-isolation rule) and calls Vanta's "Manage Vanta API" (`api.vanta.com`) with scope `vanta-api.all:read`.

### Where the current implementation lives

Nowhere yet — `vanta-mcp` is an empty scaffold (README.md only, commit f056d60). This is a from-scratch build (SOP main line A).

### Option analysis

- **Credential model**: Vanta's Manage Vanta API uses OAuth2 client_credentials (client id + secret → short-lived Bearer token), not a single static API key like several other connectors in this org. Chosen: read both `client_id` and `client_secret` from two separate Headers (`X-Vanta-Client-Id`, `X-Vanta-Client-Secret`) and do the token exchange server-side on every call. Alternative considered: let the caller pass a pre-fetched Bearer token directly — rejected, because Vanta tokens expire in 3600s and tenants would have to re-mint them out-of-band, which the gateway's Header model isn't built for.
- **Tool granularity**: one tool per resource, each supporting list-with-filters when `id` is omitted and get-by-id when `id` is given. Alternative considered: 14 separate `list_*`/`get_*` tools (the literal 1:1 mirror of Vanta's REST endpoints) — rejected per the "tools are capabilities, not API mirrors — merge overlapping tools" rule; the two endpoints per resource return the same object shape and serve the same underlying need, so merging halves the tool count (7 vs. 14, both well under the 20-tool ceiling) with no loss of capability.
- **Scope**: hardcode `vanta-api.all:read`. Alternative considered: accept scope as a Header so callers could request `vanta-api.all:write` later — rejected, since v1 has no write tool to use that scope with and exposing it would only invite confusion about what's actually implemented.
- **Base URL**: hardcode `https://api.vanta.com`. Alternative: make the host Header-configurable to support Vanta Gov — rejected for v1 as unneeded complexity (see OQ2); regional subdomains (`api.eu.vanta.com`, `api.aus.vanta.com`) already 308-redirect to the primary host per Vanta's own docs, so no MSPbots-side handling is needed for those.
- **Response field selection**: return a curated subset of each Vanta object's fields (see Data & API contract) rather than passing the full object through. Alternative: pass-through — rejected per the SOP's token-economy rule (only return the fields a tool actually needs); fields like a control's `customFields`/`implementationDetails` or a vendor's `contractAmount`/`engagements` aren't relevant to the compliance/offboarding/security-review use case this ticket describes, and can be added back if a concrete need shows up later.

### Data & API contract

Auth (per call, not cached across calls):

```
POST https://api.vanta.com/oauth/token
Content-Type: application/json
{"grant_type": "client_credentials", "client_id": "<X-Vanta-Client-Id>",
 "client_secret": "<X-Vanta-Client-Secret>", "scope": "vanta-api.all:read"}
→ {"access_token": "...", "token_type": "Bearer", "expires_in": 3600}
```
Subsequent calls: `Authorization: Bearer <access_token>` against `https://api.vanta.com/<resource>`.

Credential headers (for `mcppub register` → `credential_fields`, used when the dev leg first deploys this repo):

| Header | label | type | required |
|---|---|---|---|
| `X-Vanta-Client-Id` | Client ID | str | yes |
| `X-Vanta-Client-Secret` | Client Secret | password | yes |

- List mode (`id` omitted): `{"data": [...], "has_more": bool, "next_cursor": str | null}`

Error mapping (Vanta → our structured envelope `{"error":{"code","message","retryable"}}`):

| Vanta status | our `code` | `retryable` |
|---|---|---|
| token 400/401 (bad client id/secret) | `unauthorized` | false |
| API 401/403 | `unauthorized` | false |
| API 404 (get-by-id only) | `not_found` | false |
| API 400/422 | `invalid_argument` | false |
| token or API 429 | `rate_limited` | true (after ≤2 bounded retries respecting `Retry-After`) |
| API 500/503/504 | `upstream_error` | true |
| missing required Header(s) | 401, body lists `X-Vanta-Client-Id`/`X-Vanta-Client-Secret` | — |

### Key flow / sequence

```
Agent → Gateway (adds X-Vanta-Client-Id / X-Vanta-Client-Secret from tenant's stored credential)
  → POST /mcp tools/call vanta_get_<resource>
    → middleware: read Headers into ContextVar; 401 if either is missing
    → auth.py: POST https://api.vanta.com/oauth/token (client_credentials, scope=vanta-api.all:read)
      → 400/401 → map to unauthorized, return structured error, done
      → 429 → bounded retry respecting Retry-After, else rate_limited
      → access_token
    → client.py: GET https://api.vanta.com/<resource>[/{id}] with Authorization: Bearer <access_token>
      → map status per Error mapping table
      → success: map Vanta fields → curated tool response, map pageInfo → has_more/next_cursor
    → ContextVar reset() in finally (isolation)
  ← structured JSON response
```

### Non-functional

- **Statelessness / isolation**: `stateless_http=True`; credentials and the OAuth access token live only in a per-request `ContextVar`, reset in `finally`; no module-level or global storage of any tenant's credentials, token, or Vanta data.
- **Rate-limit risk (call out, not silently absorbed)**: Vanta's token endpoint is limited to 5 requests/minute *shared across all of that OAuth client's API usage*. Because tokens must not be cached across requests (the isolation rule above), a tenant that drives more than ~5 tool calls/minute on the same Vanta client credentials will start hitting 429 on the token endpoint — this is a vendor-imposed ceiling, not something this connector's design can raise. Mitigation: bounded retry (≤2 attempts) respecting `Retry-After`, then a clean `rate_limited` error so the agent/caller can back off rather than the connector hanging or 500ing. No current MSPbots tenant traffic volume is known, so this is flagged as an operational risk to watch post-launch, not solved by redesign.
- **Performance**: outbound timeouts 5s connect / 30s read; limited retry with backoff on 429/5xx; single tool call budget < 120s; one shared `httpx.AsyncClient` reused across requests (connection pooling only — no per-tenant data cached on it).
- **Security**: credentials read only from the two declared Headers, never logged, never written to disk; `.env`/`.venv` gitignored; `gitleaks detect` run before delivery; no real Vanta credentials anywhere in the repo (README examples use placeholders).
- **Multi-tenant isolation**: every field above (ContextVar, no caching, per-request token exchange) exists specifically so that one tenant's Vanta data can never leak into a concurrent request from another tenant sharing the same running container.
- **Observability**: structured log line on every upstream error (status, Vanta's own `message`, our mapped `code`) — never the credential values.

### Rollout & rollback

- Brand-new repo, zero existing tenants connected — there is nothing to migrate and no backward-compatibility constraint.
- First deploy uses `/api/vendor-register` (not `/api/deploy-int`), since the INT gateway does not know about `vanta` yet: `name=vanta`, `display_name=Vanta`, `repo=MSPbotsAIFramework/vanta-mcp`, `credential_fields` as listed above. Registration runs the repo's tests once on `main` before registering/deploying — a failing test blocks registration, so there's no path to a broken first deploy.
- Rollback: before any tenant has connected a Vanta credential, rollback is simply "don't register this version" / revert the commit on `main`. After the first registration, `/api/deploy-int` deploys `main` as-is on every subsequent change — the usual MCP rollback is to revert on `main` and redeploy.
